## 1. Безопасность

### 🔴 Админка и кабинет преподавателя защищены только layout'ом
17 страниц в `(admin)/admin/**` и `teacher/groups/new` не вызывают
`requireAdmin`/`requireTeacher` — проверка роли есть только в `layout.tsx`.
В App Router layout не перерисовывается при клиентской навигации, и запрос
RSC-пейлоада страницы с подделанным заголовком `Next-Router-State-Tree`
рендерит страницу **без** layout. То есть данные админки (список студентов,
заявки с телефонами) потенциально отдаются без проверки роли.

**Исправление:** проверка роли в каждой странице (или, правильнее, в функциях
слоя данных, которые эти страницы вызывают).

### 🔴 Создание платежа без авторизации, `userId` берётся из тела запроса
`api/payments/payme/create` и `api/payments/click/create`:
- не проверяют сессию — платёж создаёт кто угодно;
- `userId` приходит от клиента (`body.userId || 'guest'`) — можно создать
  платёж на чужой аккаунт; для `'guest'` падает внешний ключ → 500;
- без лимита — таблицу `Payment` можно заспамить.

**Исправление:** `authenticateRequest`, `userId` только из сессии, rate limit.

### 🔴 Оплата не доведена: нет колбэков провайдеров
Нет обработчиков Payme (`CheckPerformTransaction`, `CreateTransaction`,
`PerformTransaction`, `CancelTransaction`…) и Click (`prepare`/`complete`).
Платёж создаётся и навсегда остаётся `pending`, доступ к курсу автоматически
не выдаётся. Для «под ключ» это обязательный блок.

### 🟠 Подтверждение почты не атомарно (`api/verify`)
Сначала проверка `usedAt`, потом отдельный `update`. В сбросе пароля это уже
сделано правильно через `updateMany where usedAt: null` — повторить здесь.

### 🟠 Валидация входа в API
Zod используется только в `contact` и `lessons/step`. Остальные роуты читают
`req.json()` как есть и полагаются на ручные проверки и `as any`. Нужна
единая схема на каждый роут.

### 🟡 Мелочи
- `api/sms/callback` и `api/zoom/recordings` — заглушки, принимают любой запрос.
- `api/verify` редиректит на `NEXTAUTH_URL || ''` — при пустой переменной
  получится относительный редирект `/ru/signin`, работает случайно.

### ✅ Что сделано хорошо
- Все 15 файлов server actions проверяют роль в каждой экспортируемой функции.
- Rate limit хранится в БД (работает на serverless), правила собраны в одном месте.
- `userId` в учебных API берётся из сессии, доступ проверяется через `Enrollment`.
- `next.config.js`: открытый прокси картинок закрыт.
- Мобильные bearer-токены отделены от веб-сессии своим секретом.

## 2. Архитектура

### 🟠 Нет слоя данных
66 файлов в `app/` пишут запросы Prisma прямо в странице. Следствия:
одинаковые выборки дублируются, проверки доступа размазаны, страницы
по 300–400 строк (`teacher/groups/[id]` — 416, `signup` — 415).

**Цель:** `features/<домен>/queries.ts` (чтение) + `actions.ts` (запись),
каждая функция сама проверяет права. Страница только вызывает и рисует.

### 🟠 Нет состояний загрузки и ошибок
Ни одного `loading.tsx`, `error.tsx`, `not-found.tsx` на 67 страниц: при
медленной базе пользователь видит пустой экран, при ошибке — стандартную
страницу Next.

### 🟡 Структура `features/`
В целом разумная (по доменам), но:
- `features/ui/components` — 28 компонентов вперемешку: примитивы (Button),
  оформление (Sticker*, Boiling*, Confetti, RoughFilters) и каркас
  (SiteHeader, SiteFooter, UserMenu). Нужно разделить на `ui/` (примитивы)
  и `layout/` (каркас).
- Server actions разбросаны: `admin/actions.ts` + 7 файлов `*Actions.ts`.
- `teacher/` и `teachers/` — разные вещи с почти одинаковым названием.

### 🟡 i18n
Публичная часть переведена (`ru`/`uz`/`en`, ~980 ключей, в `uz` на 6 строк
больше — рассинхрон). Админка и кабинет преподавателя (~43 файла) — строки на
русском прямо в JSX. Решить: либо админка официально только на русском, либо
переводить. Рекомендация — оставить русской, но вынести строки в словарь.

## 3. Стили и дизайн — главная причина «каши»

- **Три подхода одновременно:** глобальные классы (`globals.css`, 5 000 строк),
  инлайн `style={{ color: 'var(--muted)' }}` (412 мест) и Tailwind (~140).
- **Слои истории дизайна:** Vertex → Highgate, золото → новый бренд,
  ChunkyButton → Button, «playful» стикеры, rough.js-иконки, notebook-фон.
  Каждая итерация оставила свой CSS.
- `tailwind.config.ts` — остаток от v3, Tailwind v4 его не читает.
- `!important` — 10 мест, 21 дублирующийся селектор, ~95 мёртвых классов.
- 45 hex-цветов в компонентах в обход токенов.

**Решение:** новый дизайн (iOS-подобный, см. артефакт), новая система токенов
и **один** способ стилизации. Старые CSS-файлы удаляются по мере переноса
страниц, а не правятся.
